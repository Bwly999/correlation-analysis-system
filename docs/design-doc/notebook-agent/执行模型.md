# 执行模型

本文档定义 Pyodide Worker 内代码执行的语义、stdout 处理、超时与中断、Worker 生命周期。

---

## 1. 核心语义：无状态执行

**这是 Notebook Agent 与 Jupyter Notebook 的最大差异**。

| 维度 | Jupyter | Notebook Agent |
|------|---------|----------------|
| 跨 cell 变量 | ✅ 持久 | ❌ 隔离 |
| 跨 cell import | ✅ 持久 | ✅ 持久（缓存共享）|
| 心智模型 | "状态机 REPL" | "`python -c` 风格的脚本" |

### 1.1 为什么选无状态

- **可重跑、可重现**：每次 exec 是自包含脚本，外部观察者能复现 Agent 的操作
- **prompt injection 抗性更强**：上一次 exec 注入的恶意符号不会污染下一次
- **简化 Worker 重启逻辑**：Worker 崩溃后无需"重放历史 cell"
- **强制 Agent 像 Claude Code 那样工作**：每次写自包含代码，不是 "df 在哪儿用 df 在哪儿"
- **跟 fs_read/fs_write 心智一致**：状态唯一靠落盘文件传递

### 1.2 实现规则

每次 `python_exec_inline` / `python_exec_file` 调用：

1. 创建一个**新的 globals dict**：`scratchGlobals = pyodide.toPy({})`
2. 调用 `pyodide.runPythonAsync(code, { globals: scratchGlobals, locals: scratchGlobals })`
3. exec 结束后丢弃 `scratchGlobals`

**Pyodide 内部 `sys.modules` 不重置**——这意味着：

- `import pandas as pd` 第一次约 500ms（动态链接 .so），后续每次 ~5ms
- 不存在 "上一个 cell 的 `df` 在这个 cell 里能直接用" 的情况
- Agent 必须在每次需要数据时重新 `pd.read_csv('inputs/data.csv')`

### 1.3 对 Agent 行为的影响

system prompt 必须明确告知 Agent：

```
执行规则（必须遵守）：
- 每次 python_exec_* 都是独立脚本，不会保留上次定义的变量
- 想用某个数据，每次都要重新 pd.read_csv() 或 fs_read()
- 想跨多步保留中间结果，把中间结果落盘到 artifacts/，下一步再读回来
- 这跟 Jupyter 不同，跟 `python -c "..."` 一致
```

## 2. stdout / stderr 处理

### 2.1 每次 exec 独立 buffer

每次 exec 开始时，Worker 内 Python 端重定向 sys.stdout / sys.stderr 到一个本次专属的 `io.StringIO`。exec 结束时取出全文返回。

```python
# Worker 内部伪码
import io
import sys
from contextlib import redirect_stdout, redirect_stderr

def run_one_exec(code: str, exec_id: str):
    out_buf = io.StringIO()
    err_buf = io.StringIO()
    with redirect_stdout(out_buf), redirect_stderr(err_buf):
        try:
            exec(code, scratch_globals)
            status = 'ok'
        except KeyboardInterrupt:
            status = 'interrupted'
        except Exception as e:
            status = 'error'
            err_buf.write(traceback.format_exc())
    return {
        'execId': exec_id,
        'stdout': out_buf.getvalue(),
        'stderr': err_buf.getvalue(),
        'status': status,
    }
```

### 2.2 流式推送

stdout/stderr 同时**流式推送**给 iframe（不只是结束时一次性返回）。

实现方式：用自定义的 `WriteableProxy` 在每次 `write(chunk)` 时同时：

1. 写到本地 buffer（用于最后构造完整 result）
2. `postMessage('stdout', { execId, stream, text: chunk })`

iframe 收到流式 chunk 后实时渲染到 UI（用户看到 print 实时滚动），同时累计成完整文本，最后返回给 Agent。

### 2.3 Agent 看到的内容

Agent 拿到的工具返回（`tool-result` 回传体）：

```json
{
  "execId": "exec_42",
  "status": "ok",
  "stdout": "完整的 stdout 文本...",
  "stderr": "完整的 stderr 文本...",
  "elapsedMs": 234
}
```

每次 exec 的 stdout/stderr **不会**累计到 Agent 上下文跨调用——只在本次工具返回里出现。

## 3. 中断与超时

启用了 COI，所以可用 SharedArrayBuffer 做协作式中断。

### 3.1 双段超时

| 阶段 | 时长 | 动作 | 影响 |
|------|------|------|------|
| 软超时（默认）| 60s | `Atomics.store(interruptBuffer, 0, 2)` 触发 SIGINT | Pyodide 在下一字节码 tick 抛 KeyboardInterrupt；kernel 存活；exec 状态 = `interrupted` |
| 硬超时（兜底）| 90s | `worker.terminate()` | Worker 进程级杀死；iframe 自动重建 Worker；状态 = `timeout` |

### 3.2 时序

```
iframe 收到 exec 请求 → 启动 timer(60s, 90s)

  60s 到了软超时 → Atomics.store interrupt = 2
       ↓
       Worker 在 5-200ms 内响应（取决于 Python 当前在做什么）
       ↓
       postMessage('exec_done', { status: 'interrupted' })
       → iframe 取消 90s timer

  Worker 没响应（Python 在 C 扩展长循环里不响应 SIGINT）
       ↓
  90s 到了硬超时 → worker.terminate()
       ↓
       iframe new Worker(...)，重新初始化 Pyodide
       ↓
       iframe 通知 Agent："环境已重启"
```

### 3.3 用户主动中断

UI 上的"停止"按钮：

```
用户点停止 → iframe 触发软中断（不等 60s）
  ↓ 5s 内 Worker 没响应
  ↓
iframe 触发硬终止 + 重启
```

### 3.4 用户主动结束 session

用户关闭笔记本：

```
有正在跑的 exec → 弹确认 "Agent 正在执行，确认中断？"
  → 确认 → 立即软中断 + 5s 兜底硬终止
  → 销毁 Worker
  → 销毁 iframe
```

### 3.5 SAB 不可用时的降级（理论上不会发生）

如果运行时检测到 `crossOriginIsolated === false`（COI 头配置失败），Worker 仍可启动，但中断只能走 `worker.terminate()`：

- 软超时直接走硬路径
- 用户主动中断 = 硬终止 + 重启
- iframe 启动时检测到这种情况 → 顶部条幅警告 "Python 环境受限，长时间任务无法干净中断"

正常发布版本必须保证 COI 启用，本路径仅作运维容错。

## 4. import 缓存共享细节

`sys.modules` 在 Pyodide 内是单例字典，跨 exec 共享。这意味着：

| 场景 | 行为 |
|------|------|
| `import pandas as pd` 在 exec_1 第一次 | ~500ms 加载，pd 进 sys.modules |
| `import pandas as pd` 在 exec_2 | ~5ms（仅创建新别名），pd 复用同一对象 |
| 修改 `pd.x = 1` in exec_1 | exec_2 里 `import pandas as pd; pd.x` 仍是 1（共享对象）|
| `del sys.modules['pandas']` in exec_1 | exec_2 里 `import pandas` 重新加载 |

**风险**：Agent 在某次 exec 修改了 `pandas` 类的属性，下次 exec 受影响。

**对策**：

- system prompt 警告 Agent **不要 monkey-patch 标准库**
- 如发现行为异常，Agent 可以主动调 `python_kernel_reset`（M2 加；M1 让用户手动重启 Worker）
- 监控：iframe 检测到连续 N 次 exec 都是相同代码却结果不同 → 提示用户重启

### 4.1 micropip 安装的状态

M1 锁死 micropip。所有可用包都来自启动时预加载列表（见 [部署与构建](部署与构建.md#默认包列表)）。

M2 放开 micropip 白名单时：

- 安装的包一直存在 sys.modules 直到 Worker 重启
- 安装记录写到 OPFS `.session.json`，用于 Worker 重启后自动重装

## 5. Worker 生命周期

### 5.1 创建

```
iframe 启动 → new Worker('/notebook/worker.js', { type: 'module' })
↓
postMessage('init', { indexURL, packages })
↓
Worker：loadPyodide({ indexURL, fullStdLib: false })
       ↓ (~5s 解析 wasm)
       ↓ (~10s 加载默认包)
       ↓
       挂载 NODEFS / OPFS
       ↓
       锁定 jsglobals（删 fetch/XHR/WS/IDB/caches）
       ↓
       加载 Python 端的 sandbox 初始化代码（重定向 stdout 等）
       ↓
postMessage('init_done')
```

预期耗时：首次 ~30s（无浏览器缓存），后续 ~5s（Service Worker 命中）。

### 5.2 重启触发条件

| 触发 | 处理 |
|------|------|
| 硬超时 terminate | iframe 自动重建 + 通知 Agent |
| Worker 崩溃（OOM / wasm 异常）| iframe `worker.onerror` 捕获 → 重建 |
| 用户点 "重启 Python 环境" 按钮 | iframe 主动 terminate + 重建 |
| Pi Agent 调 `python_kernel_reset` 工具（M2）| 同上 |

### 5.3 重启对 Agent 的告知

iframe 内 WorkerHost 自动重启成功（init_done）后，触发 `onAutoRestarted` 回调，runtime 完成：

1. 把 OPFS 里的 `inputs/`、`scripts/` 重新灌回新 Worker 的 MEMFS（`syncOpfsFilesToWorker`）
2. 调 `notifyNotebookEnvironmentChanged(sessionId, message)` → `POST /api/notebook-agent/sessions/:id/system-message` → gateway 用 Pi SDK `session.sendCustomMessage({ customType: 'environment_notice', ... }, { deliverAs: 'nextTurn' })` 把下面这条 system message 挂到下一条用户消息之前作上下文（不触发独立 turn，不打断当前流）：

```
[Notebook 系统消息] Python 运行时已自动重启（执行超时或崩溃自愈）。
Workspace 文件已保留，但内存中的变量、已 import 的模块、已加载的 DataFrame 均已失效。
下一次操作前请重新加载数据。
```

> `deliverAs: 'nextTurn'` 是 Pi SDK 的 "aside" 机制：消息挂在下一次 `prompt()` 的上下文里，Agent 下一轮即能看到。若 SDK 调用异常，gateway 退化为 `session.steer(message)`（当前 turn 结束后注入）。注入失败静默——这是 best-effort 的可观测性增强，不阻塞重启主流程。

### 5.4 重启的边界

- Worker 重启**不影响** OPFS 文件
- Worker 重启**不影响** Pi Agent session（推理状态由后端保管）
- Worker 重启 = 一次"局部失败"，不是"session 中断"
- 用户视角：UI 上有一个明显的"环境已重启"提示（吐司 + 顶部细条幅 5s 后消失）

## 6. 并发约束

### 6.1 单 Worker，串行 exec

同一时刻最多一个 exec 在跑。Agent 不会并发调多个 python_exec_*（Pi SDK 的工具调用本身是串行的）。

如果 iframe 收到第二个 exec 请求时第一个还在跑：

- iframe 直接拒绝并返回错误 "已有正在执行的 exec"
- 这种情况只能发生在客户端 bug 时；Agent 正常使用不会触发

### 6.2 fs_* 与 exec 的关系

fs_* 工具**全部在 iframe 主线程执行**（不进 Worker），所以可以与 Worker 内的 exec 并发：

- Agent 在 exec 跑的过程中可以调 fs_read 看其他文件（理论上 LLM 不会这样，但协议允许）
- iframe 文件树的轮询读 OPFS 与 Worker NODEFS 写在不同时机，可能短暂不一致 —— 接受这种"最终一致"

### 6.3 单 session 单 Worker

不允许一个 session 起多个 Worker。Worker 数 = session 数 = 1（Q11 决策）。

iframe 维护以下指标，UI 上以"环境状态卡片"展示：

| 指标 | 来源 | 刷新频率 |

## 8. 错误传播

### 8.1 Python 异常

Python 抛出未捕获异常时，Worker 返回：

```json
{
  "kind": "exec_done",
  "execId": "...",
  "status": "error",
  "stdout": "...",
  "stderr": "Traceback...\nValueError: ...",
  "error": {
    "type": "ValueError",
    "message": "...",
    "traceback": "完整 traceback"
  },
  "elapsedMs": 12
}
```

Agent 拿到 stderr + traceback，可以决定下一步（修代码 / ask_user）。

### 8.2 工具协议错误

JSON schema 校验失败、路径越界、配额耗尽等：

```json
{
  "tool": "fs_write",
  "ok": false,
  "error": {
    "code": "path_out_of_workspace",
    "message": "路径必须以 inputs/scripts/artifacts/reports 之一开头"
  }
}
```

错误码列表见 [工具集协议](工具集协议.md#错误码)。
