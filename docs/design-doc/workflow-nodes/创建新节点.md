# 创建新节点

本文档描述新增节点的完整规则和推荐流程。

> 前置阅读：[节点清单](节点清单.md) — 了解现有节点体系
> [节点定义与属性](节点定义与属性.md) — `NodeDefinition` / `NodeProperty` 设计

---

## 1. 先判断节点类别

创建前先回答三个问题：

1. **它是流程入口、中间处理还是流程终点？**
2. **单输入还是多输入？**
3. **输出更像表格、报告、图表还是导出文件？**

### 分类原则

| 类别 | 判断标准 |
|------|---------|
| **Trigger** | 能独立产生源数据或运行时入口 |
| **Action** | 依赖上游数据继续加工 |
| **Terminal** | 作为最终产物展示、分析或导出 |

### 禁止

- 把本应是 Terminal 的节点做成 Action 以绕过连接限制
- 把本应是多输入的节点硬塞成单输入

---

## 2. 必须走声明式注册

新增节点流程：

1. 在 `src/nodes/definitions/` 下新增定义文件
2. 在 `src/nodes/registry.ts` 中注册
3. 补齐图标、显示名、描述、属性定义
4. 在 `helpCatalog.ts` 的 `nodeLibraryGroups` 中添加分组映射
5. 确认节点库可以正常显示与搜索

### 默认约定

- 新节点默认 `availability = 'active'`
- 只有明确用于历史回放兼容的节点才标记 `legacy`

### 禁止

- 在画布组件中硬编码节点类型
- 在弹窗组件中用分支把新节点"特殊接进去"
- 在 `NodeSidebar` 中单独维护分组/别名/关键词映射表

### libraryGroup 映射说明

`libraryGroup` 不在 `NodeDefinition` 文件中硬编码，而是在 `helpCatalog.ts` 的 `nodeLibraryGroups` 对象中统一维护：

```ts
const nodeLibraryGroups: Record<string, NodeLibraryGroupId> = {
  'your-node-name': 'your-group-id',
  // ...
}
```

新增节点时必须添加对应的映射，否则在 `NodeSidebar` 中会回退到 `misc` 分组。

---

## 3. 输出必须遵循标准结果协议

| 数据类型 | NodeResult kind |
|---------|----------------|
| 表格 | `table` |
| 多组表格 | `tableCollection` |
| 分析结论 | `report` |
| 图表 | `chart` |
| 导出结果 | `file` |
| 其他结构化对象 | `json` |

### 规范

- 不允许新增旧版 `{ data: ... }` 执行输出桥
- 尽量补齐 `schema`、`meta`、`preview`
- 需要字段来源追踪时写入 `lineage`

---

## 4. 输入协议必须清晰

- 单输入节点直接消费上游 `NodeResult`
- 多输入节点必须消费 `MultipleNodeExecutionInput` 协议
- 多输入节点统一读取 `inputs[].result`
- 不允许新增旧版 `payload` alias 兼容写法回流到执行链

---

## 5. 属性设计必须可维护

- 配置设计优先让用户"直接可理解"，不是让实现"勉强可用"
- 同一类参数命名要稳定，例如 `targetColumn`、`groupBy`、`conditions`
- 不要在一个节点里混入两套互斥心智模型；必要时拆节点或用模式切换
- 如果某节点配置复杂到必须靠大量说明文字才能理解，优先重构属性结构

具体设计规范见 [节点定义与属性](节点定义与属性.md#nodeproperty-设计规则)。

---

## 6. 帮助与 LLM 提示规范

所有节点必须补齐帮助信息。

### help 最小集

| 字段 | 内容 |
|------|------|
| `summary` | 一句话说明节点用途（帮助中心索引 + 节点帮助头部复用） |
| `whenToUse` | 适用场景，帮助用户判断是否应选此节点 |
| `inputGuide` | 输入要求、前置节点或连接约束 |
| `outputGuide` | 输出结果形态与可衔接的下一步 |
| `parameterGuide` | 按节点复杂度补充关键参数说明 |
| `commonIssues` | 常见问题与解决（可选但推荐） |

### assistantHints 最小集

| 字段 | 说明 |
|------|------|
| `useCases` | 使用场景列表 |
| `keywords` | 搜索关键词 |
| `workflowRoles` | 在工作流中的角色 |
| `recommendedPrevNodes` | 推荐的上游节点 |
| `recommendedNextNodes` | 推荐的下游节点 |

### 维护约束

- 帮助中心中的节点摘要统一复用 `NodeDefinition.help.summary`
- 节点配置弹窗中的帮助详情统一读取 `NodeDefinition.help`
- 不允许在工作流组件中维护第二套节点帮助映射表
- 新增节点时，缺少 help 最小集视为节点定义未完成

---

## 7. 预览与 viewer 规范

- 常规表格、分组表格、JSON 优先复用现有 viewer 体系
- 若需要专用 viewer，先在 `preview.viewer` 中声明
- 再到 `src/components/workflow/viewers/registry.ts` 中注册
- 不要把专用预览逻辑散落到多个工作流组件里
- 新增或调整 viewer 时，要同时确认节点详情弹窗与工作流结果看板都能正确复用

现有 viewer 清单见 `../workflow-system/结果展示链路.md`。

---

## 8. 历史与持久化兼容

新增节点时确认：

- 节点输出是否可以安全进入历史快照
- 大结果是否需要截断
- 是否会给 `SavedWorkflow` / `ExecutionRecord` 带来异常体积
- 节点在历史模式下是否仍能被正确只读展示

---

## 9. 测试规范

至少覆盖：

| 测试类型 | 说明 |
|---------|------|
| execute() 核心逻辑 | 正常输入、边界输入、空输入 |
| 标准结果协议 | 输出是否可标准化到 `NodeResult` |
| 多输入协议 | 如适用，验证 `MultipleNodeExecutionInput` 消费 |
| 帮助最小集 | 至少断言 `help.summary`、`whenToUse`、`inputGuide`、`outputGuide` |
| 工作流执行链 | 如影响运行时，写 `workflowStore` 回归 |
| viewer / 预览 | 如新增专用展示，验证 viewer 渲染 |

### 优先落点

- `src/nodes/__tests__/`
- `src/stores/__tests__/`

---

## 10. 推荐落地流程

建议按以下顺序开发新节点：

1. **文档先行** — 在本文档中补充节点定位与规则
2. **设计接口** — `NodeDefinition`、属性定义、输入输出类型
3. **实现逻辑** — `execute()`，确保返回标准 `NodeResult`
4. **注册节点** — `registry.ts` + 确认节点库显示
5. **补齐元数据** — `helpCatalog.ts` 中的 help + `assistantHints` + `libraryGroup` 映射
6. **补 preview/viewer** — 如需专用 viewer，注册并在 preview 中声明
7. **测试覆盖** — 节点测试 + 工作流回归测试
8. **同步文档** — 若影响系统级协议，更新 `../workflow-system/`

---

## 11. 更新本文档的时机

以下情况应同步更新本文档根目录下的对应文件：

- 节点新增、删除、改名、改类别 → [节点清单](节点清单.md)
- `NodeDefinition` / `NodeProperty` 设计变化 → [节点定义与属性](节点定义与属性.md)
- 创建规范、测试规范、viewer 规范变化 → [创建新节点](创建新节点.md)
- 历史兼容性变更 → [附录-历史补充说明](附录-历史补充说明.md)

若只涉及执行链、结果协议、持久化、viewer 注册体系等系统级规则，则更新 `../workflow-system/` 目录。
