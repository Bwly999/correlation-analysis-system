## 0. 系统全貌（30 秒电梯陈述）

这是一个**制造业质量数据分析的低代码平台**。两类用户工作范式并存：

- **画布（Workflow）**：拖拽 ~30 个节点搭分析流程，系统拓扑执行、产出图文报告。给人和 Agent 共同用的「显式编排」工具。
- **笔记本（Notebook）**：AI Agent 在浏览器 Pyodide 沙箱里写 Python 自由分析。给 Agent「黑盒分析」的工具。

系统里有**三个相互独立、零耦合的 AI Agent 子系统**：

| Agent | 入口 | 角色 | 工具 |
|------|------|------|------|
| **Pi Agent 主链** | `/api/pi-agent/*` | 工作流画布的自然语言编排助手 | 画布工具（workflow_*）|
| **JS Transform Agent** | `/api/js-transform-agent/*` | `js-transform` 节点的代码编程助手 | 节点工具（js_*）|
| **Notebook Agent** | `/api/notebook-agent/*` | Pyodide 自由分析笔记本 | Notebook 工具（python_exec_*、fs_*）|

> 注意：曾经还有「workflow-ai」（Vercel AI SDK 直接生成工作流）和「opencode」（OpenCode/MCP）两条 Agent 链路，**都已废弃并保留 404 回归测试**。当前生产方案是基于 `@earendil-works/pi-coding-agent` SDK 的工具调用 Agent。用户提到"工作流里的 pi agent 除了 js 节点都已停用"——准确说是：**JS Transform Agent 还在用**（它是 `js-transform` 节点的编程助手），工作流编排那条主链在产品上停用了，但代码仍在。

三者复用同一套**运行时基础设施**（`runtimeFactory.ts` 模型加载、`frontendBridge.ts` 工具桥接、`eventBridge.ts` 事件转换），但 Session、工具集、状态机完全独立。

## 一、Agent 核心架构：前端执行 + 后端调度

### 1.1 核心矛盾与解法

**矛盾**：Agent 需要调用工具来"改变世界"——修改画布、执行工作流、运行 Python。但这些动作的**真实状态都在浏览器内存里**（Vue 响应式 store、Pyodide Worker），后端根本够不到。如果让后端直接维护一份画布状态，就会产生"两份状态、需要同步"的地狱。

**解法 —— FrontendBridge 模式**（`src/server/piAgent/frontendBridge.ts`）：

后端 Agent 只做两件事：①LLM 推理 ②工具调度。当 Agent 决定调用工具时，后端不执行工具，而是：

```
1. 后端 defineTool 的 execute() 里调用 bridge.request(toolCallId, toolName, params)
   → 返回一个挂起的 Promise，同时启动超时定时器
2. bridge 通过回调把 {type:'tool.execute', toolCallId, toolName, params} 推到 SSE 事件流
3. 前端收到 tool.execute 事件 → 路由到对应的执行器（WorkflowApi / Worker / OPFS）
4. 前端执行完，POST /api/.../tool-result 把结果回传后端
5. 后端 resolvePiAgentToolResult → bridge.resolveResult(toolCallId, result)
6. 第 1 步挂起的 Promise 被 resolve，Agent 拿到结果继续推理
```

**关键设计点**：
- **toolCallId 配对**：Pi SDK 给每次工具调用分配的唯一 ID，前后端靠它配对请求与响应
- **超时 + 续期**：画布操作 90s、工作流执行 600s（Python 可能跑很久）；前端每 10s POST 一次 `tool-progress` 续期（`touchRequest` 重置定时器），防止长任务被误杀
- **用户级隔离**：每个用户会话（PiAgentRuntime）持有独立的 FrontendBridge 实例，pendingRequests Map 互不干扰
- **优雅退出**：会话关闭时 `dispose()` 把所有挂起 Promise 全 reject，避免内存泄漏

**为什么不直接把工具实现放后端？**
- 画布状态是 Vue Flow + Pinia，搬到后端要重写整个前端
- Python 必须在浏览器（Pyodide），后端没有沙箱
- 这套设计让"工具执行端"完全可插拔：同一个 Pi SDK 会话，前端执行器可以是画布、可以是 Worker、可以是任何东西

> 锚点：`src/server/piAgent/frontendBridge.ts:88`（request）、`:126`（resolveResult）、`:153`（touchRequest）、`src/server/piAgent/gateway.ts:502`（resolvePiAgentToolResult）

### 1.2 Session 生命周期与状态机

每个 Agent 会话在后端是一个 `PiAgentRuntime` 对象，存在内存 Map 里（`gateway.ts:70`）。核心字段：

```ts
interface PiAgentRuntime {
  session: AgentSession          // Pi SDK 的会话对象
  runState: 'idle'|'running'|'completed'|'interrupted'|'failed'
  activeTurnState: 'responding'|'tooling'|'idle'|'interrupted'|'failed'
  pendingFollowUps: string[]     // 用户在 Agent 思考时连续发的消息排队
  eventListeners: Set<...>       // SSE 事件流订阅者
  bridge: FrontendBridge
}
```

**消息发送的四种分支**（`gateway.ts:264` `sendPiAgentMessage`）—— 这是面试时很能体现细节的点：

| 当前态 | 用户发消息 | 调用 |
|-------|-----------|------|
| `responding`（正在生成文字）| 立即插话 | `session.followUp(msg)` |
| `tooling`（正在等工具结果）| 排队 | push 进 pendingFollowUps + `followUp` |
| 上一条以 toolResult 结束 + 用户说"继续" | 续跑 | `session.agent.continue()` |
| 其他（空闲）| 新对话 | `session.prompt(msg)` |

这套状态机解决了"用户在 Agent 思考时还能不能说话、说了怎么处理"的体验问题。

### 1.3 工具的「共享 spec 驱动」注册机制

工具不是前后端各写一份，而是**单源真相**：`src/shared/piWorkflowTools.ts` 声明所有工具的 spec（name / target / riskLevel / executorKey），前后端都按 `executorKey` 建 registry。

```ts
// shared/piWorkflowTools.ts
{
  name: 'workflow_update_partial_workflow',
  target: 'frontend_canvas',      // 谁执行
  riskLevel: 'high',
  executorKey: 'updatePartialWorkflow',
}
```

- 后端 `tools/sharedRuntimeTools.ts` 按 `executorKey` 找 factory 实现，**找不到就初始化抛错**（"缺失即失败"原则，杜绝静默漏配）
- 前端 `piAgentStore.ts:619` `registerToolExecutors` 用同样的 spec 注册 `WorkflowApi` 方法

**工具分三类（按执行端）**：
| target | 谁执行 | 示例 |
|--------|--------|------|
| `frontend_canvas` | 前端画布 | `workflow_update_partial_workflow`、`wf_executeWorkflow` |
| `frontend_bridge` | 前端只读查询 | `workflow_get_node_catalog`、`workflow_get_node` |
| `server_runtime` | 后端直接执行 | `workflow_get_session_context`（读 request 里附带的上下文）|

**「增量修改画布」是核心创新**：早期是 `wf_addNode/wf_connectNodes` 这种原子工具（一次一个动作），后来收敛成 `workflow_update_partial_workflow`——一次提交一批 `operations`（createNode/updateNodeConfig/connectNodes/removeNode...），同批次内新建节点可以用 `id` 被后续操作引用。好处是：①减少前后端往返 ②保证一组关联修改的原子性 ③LLM 更容易表达"建一个节点并连上"的意图。

> 锚点：`src/server/piAgent/tools/atomicWorkflowTools.ts:63`（operation schema）、`:126`（updatePartialWorkflow）

## 二、Agent 的流式通信：事件流协议

> **演进说明**：事件流最初采用自研 NDJSON（一行一个 JSON），后已演进为标准 SSE（`text/event-stream`），与 OpenAI/Anthropic/Gemini 主流 LLM API 对齐，降低新人认知与抓包调试成本。此处记录最终的 SSE 实现，以及"为什么是手写 SSE 而非原生 EventSource"这一关键约束。

### 2.1 为什么是手写 SSE，而非原生 EventSource

先厘清一个易混淆点：**SSE 有两种实现，header 支持完全不同**。

| SSE 实现方式 | 自定义 header | 自动重连 | 浏览器内置解析 |
|------|-------------|---------|--------------|
| 原生 `EventSource` API | ❌ 不支持（[whatwg/html#2177](https://github.com/whatwg/html/issues/2177) 挂了多年的 spec issue）| ✅ 内置 | ✅ 内置 |
| fetch + 手写 SSE 解析 | ✅ 支持 | ❌ 要自己实现 | ❌ 要自己解析 `data:` 行 |

项目硬约束：所有请求必须走统一 axios 实例（注入 JWT + `x-workflow-user-id`），原生 `EventSource` 不走 axios、不支持自定义 header，**直接被排除**。因此采用 `fetch` + 手写 SSE 解析（`src/services/parseSseStream.ts`），既对齐业界 SSE 帧格式，又能复用统一鉴权链路。

**关于自动重连的刻意取舍**：Agent 会话有状态，SSE 原生的 `retry:/id:` 自动重连/续传反而是负担——我们要的是"断了 GET 快照手工重建"（`recoverSessionState`），不是偷偷续传。所以手写解析时主动不依赖这些字段，断线由快照恢复逻辑兜底。

### 2.2 协议实现（`src/server/http/sseStream.ts`）

```
响应头：
  Content-Type: text/event-stream; charset=utf-8
  Cache-Control: no-cache, no-transform
  X-Accel-Buffering: no          ← 关键：禁用 nginx 缓冲，否则事件会攒一批才发
```

帧格式为标准 SSE：`data: {json}\n\n`（不使用 `event:`/`id:`/`retry:` 字段——事件类型已在 JSON 的 `type` 里，重连走快照恢复而非 SSE 续传）。

- **15s 心跳**：`{type:'stream.heartbeat'}` 防止中间代理掐断空闲连接
- **首事件**：连接建立立即发 `{type:'stream.ready'}`
- **清理**：连接 `close`/`error` 时清理订阅、停心跳、unsubscribe

### 2.3 事件类型设计（`eventBridge.ts:14`）

Pi SDK 的原生事件（`agent_start`/`message_update`/`tool_execution_end`...）经过 `bridgePiEvent` 转换成前端统一的事件协议：

```
message.start         开始一条 assistant 消息
message.delta         文本增量（流式打字）
message.thinking_delta 思考链增量（reasoning）
message.completed     消息完成
tool.start / tool.end 工具调用开始/结束
tool.execute          ★ 后端要求前端执行工具（FrontendBridge 发起）
session.status        会话状态变更
session.stop_diagnosis 一轮停止的原因诊断（normal/read_only_observation_end/interrupted/failed）
follow_up_queued/drained 用户插话入队/出队
```

`session.stop_diagnosis` 是个有意思的设计：它会判断这一轮是不是"只读了上下文就停了"（`read_only_observation_end`），如果是就提示用户"本轮在读取信息后已停止，可继续追问"——解决了 LLM 偶尔"只调一个只读工具就结束、不回答问题"的体验问题（系统提示词里也明确禁止这种行为）。

### 2.4 前端消费 + 断线重连（`piAgentStore.ts:349`）

前端用 `AbortController` + axios fetch adapter 消费流，关键细节：

- **ready promise**：连接建立后 `onOpen` 才 resolve，发消息前必须等流就绪
- **断线恢复**（`recoverSessionState`）：流断了不直接报错，而是 GET `/sessions/:id` 拉一份会话快照（消息列表、工具调用、状态、停止原因），把本地状态完整重建。如果是 running 态被中断，标记成 interrupted 让用户能继续
- **快照赋值**：历史 toolCall 在快照里是平铺的，要回填到对应的 assistant 消息上（`applySessionSnapshot`）

## 三、Notebook Agent：浏览器内的 AI 数据分析沙箱（项目技术深度的天花板）

### 3.1 产品定位（面试讲清楚"为什么做这个"）

**痛点**：画布范式把 LLM 锁在"节点编排员"角色——它只能创建/连接节点，无法发挥数据分析师的真正实力（探索性分析、迭代假设、画图、写复杂 pandas）。

**Notebook Agent 把 LLM 解放成"带 Python 沙箱的数据科学家"**：用户给目标和数据，Agent 在浏览器里用 Python 自由分析，产出 `reports/main.md` + `artifacts/` 下的图表。

**关键产品决策**：「画布管流程，笔记本管洞察」。两个系统严格隔离——笔记本里 Agent 看不到画布工具，画布里 Agent 看不到笔记本工具。笔记本可以读画布某节点的输出作为输入（一次性灌入），但不能反向改画布。

### 3.2 三层进程模型

```
[ 主站窗口 ]  ←postMessage RPC→  [ iframe 窗口 ]  ←postMessage→  [ Pyodide Worker ]
   ↓ axios→服务端                       ↓ axios→服务端                    ↓ (无网络)
                                       OPFS 读写                         OPFS 读写(NODEFS)
```

为什么三层：
- **iframe**：用 Cross-Origin Isolation（COOP=same-origin + COEP=require-corp）开启 SharedArrayBuffer，Worker 中断才可用；同时和主站状态隔离
- **Worker**：Pyodide 跑在 Worker 才不阻塞 UI；崩溃了能 `terminate` + 重建
- **主站**：持有画布、做鉴权、管理 iframe 生命周期

### 3.3 六层纵深防御安全模型（这是 Notebook 最硬核的部分）

面试官最爱问"AI 跑用户代码怎么保证安全"。我们的答案是**L1~L6 六层独立失效都不应导致整体失守**：

| 层 | 防什么 | 怎么做 |
|----|--------|--------|
| **L1 WASM 沙箱** | Python 调系统 | Pyodide 是 WASM，天生没 syscall/socket/fork/真实 FS |
| **L2 iframe 边界** | XSS、iframe 逃逸 | COI 隔离 + postMessage `event.source` 强校验 + Zod schema 校验 |
| **L3 jsglobals 锁定** | Python 通过 `from js import` 拿到 Worker 的 globalThis | `loadPyodide({jsglobals: safeJsGlobals})` 只暴露 console，不暴露 fetch/globalThis/process |
| **L4 Worker 能力剥夺** | Python 通过任何途径出站 | 启动后 `delete self.XMLHttpRequest/WebSocket/EventSource/indexedDB/caches`，fetch 改成只允许同源 `/pyodide/v0.27/` 前缀的白名单 shim |
| **L5 业务超时配额** | 死循环、OOM、写满磁盘 | 单 cell 60s 软超时（SIGINT）+ 90s 硬超时（terminate）；OPFS 单 session 500MB、单次 fs_write 50MB |
| **L6 审计日志** | 事后追溯 | ring buffer 记 exec_start/done（只记 SHA-256 hash 不记代码全文）、fs_write、worker_restart；关键事件上报后端 |

**红队清单 20 项自动化回归**（`tests/notebook-agent/security/redteam.spec.ts`），每项对应一层防御：
- `from js import process` → ImportError（L3）
- `import os; os.system('rm -rf /')` → OSError（L1）
- `open('/etc/passwd')` → FileNotFoundError（L3 文件系统边界）
- fs_read 路径含 `..` → 拒绝（路径校验）
- `while True: pass` → 60s SIGINT（L5）
- Markdown 渲染 `<script>alert(1)` → 被 sanitize 拦（XSS）
- ... 共 20 项

### 3.4 双文件系统：OPFS + MEMFS 的取舍

这是 Notebook 里**最有讲头的技术决策**之一。

**问题**（三层，都能对上官方文档）：
1. **官方 `mountNativeFS` 默认不同步**——Pyodide 官方 file-system 文档原话：*"changes in the mounted file system is **not synchronized by default**, you must call syncfs()"*。这是浏览器沙盒硬限制，用官方方案也得手动 sync。
2. **官方 `mountNativeFS` 是 Experimental，仅 Chromium**——依赖 File System Access API，Firefox/Safari 不支持。
3. **项目风险登记**（`验收与基线.md:265`）：「Pyodide OPFS 直挂在 0.27.x 不够稳定 — 中级风险」。不稳的是 emscripten NODEFS → File System Access API → OPFS 这个三层集成点。

**最终方案**（双 FS + 显式 sync，**不是"自研文件系统"，是绕开不稳集成点**）：
- **持久层 = OPFS**（浏览器原生，稳）：iframe 主线程异步读写，按 sessionId 隔离
- **Python 可见层 = MEMFS**（Pyodide 自带，稳）：Worker 内虚拟 FS，只 mkdir 四个顶级目录（inputs/scripts/artifacts/reports），不挂 OPFS
- **入向 sync**：主线程读 OPFS 字节 → `workerHost.writeFs` 灌进 MEMFS
- **出向 sync**（关键）：`python_exec_*` 后主线程主动 `snapshotFs(['artifacts','reports'])` 把 MEMFS 变更拉回写 OPFS

**为什么不直接挂 OPFS**：两个稳的组件 + 一段我能 debug 的薄胶水，比赌上游黑盒集成点可靠。代价：①出向 sync 有窗口（exec 后才 snapshot），用轮询兜底 + 服务端 zip 快照恢复；②大文件双写内存翻倍（50MB/500MB 配额兜住）。

**路径校验**（`resolveSafePath`）：拒绝绝对路径、拒绝 `..` 越界、必须落在四个顶级目录内。注意 sessionId 不拼进路径——session 隔离由 `notebook-${sessionId}` 的 OPFS 目录 handle 完成。

### 3.5 中断的两段式（SharedArrayBuffer + Atomics）

```
iframe: Atomics.store(interruptBuffer, 0, 2)   // 真正的 SIGINT 信号
Worker: Pyodide 在下一个字节码 tick 抛 KeyboardInterrupt → 'interrupted'
```
- 不走 postMessage 消息（消息有延迟）
- 90s 兜底：直接 `worker.terminate()` + 自动重建 Worker（约 30s）+ 在 Agent 上下文追加 system message "Python 环境已重启"

### 3.6 bootstrap 竞态修复（一个真实踩过的坑）

**症状**：早期实现里 events 订阅就触发首轮 prompt，结果 Agent 第一轮去 `fs_list inputs/` 时 CSV 还没写完（postMessage 异步），读到空目录。

**修复**：`tryStartNotebookBootstrap()` 必须 `streamSubscribed`（已 GET /events）且 `dataReady`（已 POST /ready，即 import_csv 完成）**同时成立**才触发，且 `bootstrapStarted` 保证只触发一次。配套写了 E2E 回归测试（`e2e/notebook-bootstrap-race.spec.mjs`）。

> 这是个很好的"我踩过坑并系统性修复"的面试素材。

### 3.7 Notebook 工具集（`notebookAgent/tools.ts`）

全部走 FrontendBridge 转发，单文件统一壳：
- `python_exec_inline` / `python_exec_file`：跑 Python（120s 超时）
- `python_packages`：加载 runtime 内已有的 wheel（命中本地走同源 fetch）
- `fs_read/write/edit/list/grep`：文件操作
- `todo_write`：把分析计划同步给用户
- `ask_user`：关键决策点暂停问用户（24h 超时）

## 四、JS Transform Agent（仍在用的那个）

`js-transform` 节点的专用编程助手（`/api/js-transform-agent/*`）。用户在节点里写 JS 代码处理 `rows`，Agent 帮忙写/改/调试。

**特点**：
- 复用 Pi SDK 会话能力 + FrontendBridge
- **双模式**（`ask` / `agent`）：ask 模式只暴露 `js_get_context`（只读答疑），agent 模式才给 `js_update_code` + `js_debug_node`（能改代码并触发调试）
- 模式切换通过 `modeController` + 动态改 `session.agent.state.tools` 和 `systemPrompt` 实现
- 工具：`js_get_context`（读节点代码/输入样本）、`js_update_code`（覆盖代码，60s）、`js_debug_node`（走节点既有调试链路，600s）、`js_get_last_debug_result`
- 支持 `abort`：`session.clearQueue()` 拿回排队的 steering/followUp 消息 + `bridge.cancelPendingRequests` + `session.abort()`

> 锚点：`src/server/piAgent/jsTransformAgentGateway.ts`

## 五、工作流系统（Agent 之外的核心）

### 5.1 执行引擎（`workflowStore.ts`，约 2700 行）

- **拓扑递归执行**：单节点执行时递归跑上游；全局执行选 Terminal 节点（无则退化为叶子节点）逐个执行
- **冻结输出（isPinned）**：冻结节点的输出被复用，不重跑——支持"我只想改下游"
- **单节点调试两策略**：①调试节点（复用上游缓存）②重跑上游后调试
- **手动模拟输入**：`useManualInput + manualInput` 跳过上游，纯调试当前节点
- **运行时输入**：Trigger 缺必填参数时记 `pendingExecution`，UI 弹窗引导补参，支持多 Trigger 顺序补录
- **运行时输入持久化开关**（`persistRuntimeInputs`）：保存工作流时是否剥离运行时参数；file 类型永远不持久化
- **停止机制**：`isStopping` 标记，递归链主动检查中止

### 5.2 标准化结果协议（`nodes/result.ts`）

```ts
interface NodeResult {
  kind: 'table'|'matrix'|'report'|'chart'|'file'|'json'|'scalar'|'tableCollection'|...
  payload: T
  schema?: { fields: {name, type, nullable}[] }   // 自动字段类型推断
  preview?: { viewer: string, props?, chartDefaults? }  // 声明式 viewer 路由
}
```

- `normalizeNodeResult` 自动从行数据推断 schema（number/boolean/date/string/json/unknown）
- `defaultViewerByKind` 按 kind 默认路由到 viewer（table→table-chart-combo-viewer，report→report-viewer...）
- 提供 `createTableResult/createReportResult/createChartResult...` 工厂
- **结果类型 → viewer 解耦**：~30 个节点产出统一协议，viewer 按类型渲染，互不耦合

### 5.3 节点体系（~30 个）

| 类别 | 数量 | 代表 |
|------|------|------|
| Trigger | 3 | file-import、manual-json-import、neighbor-system（看板对接）|
| Action | 10+2 legacy | 去重、缺失/异常值处理、编码缩放、筛选、字段选择、排序、js-transform、聚合、合并（多输入）|
| Terminal | 10+5 legacy | 相关性分析、VIF、PCA、ANOVA、分类因子筛查、XGBoost+SHAP、Lasso、多元线性回归、随机森林、逻辑回归 |

- 部分 Terminal 前端纯 JS 算（相关性、VIF、PCA、ANOVA）
- 部分代理到后端 Python（XGBoost、Lasso、回归类）—— 走 `/api/analysis/*` 纯 HTTP 代理层，**不参与 Agent session**
- 多输入节点（data-merge）：append / join / collection 三种合并模式

### 5.4 连接规则与 viewer 注册

- 连接规则在 `workflow/connectionRules.ts`，约束哪些节点能连哪些
- viewer 在 `components/workflow/viewers/`，按 NodeResult.kind + preview.viewer 路由
- AG-Grid 虚拟滚动解决大数据表格、ECharts 画图、ReportViewer 渲染结构化报告

## 七、Pi SDK 模型接入（`runtimeFactory.ts`）

### 7.1 provider 自动推断

从 baseUrl 推断 provider（deepseek/anthropic/openai/openrouter/groq/mistral...），用 OpenAI-compatible API 协议接入。`buildModelFromProfile` 把用户的 profile（baseUrl/apiKey/model/contextWindow/maxTokens）转成 Pi SDK 的 Model 对象。

### 7.2 模型测试与真实运行同链路

`/api/pi-agent/model-profiles/test` 不是简单 ping，而是**用和真实运行完全一样的构建逻辑**（provider/auth/ModelRegistry/AuthStorage/DefaultResourceLoader）建一个最小会话，跑一句"请只回复 ok"。这保证了"测试通过 ≈ 真实能用"。

### 7.3 多模型预注册（Notebook 用）

Notebook 支持对话中热切换模型（`session.setModel`），要求目标模型的 apiKey 在会话创建时已注册到 authStorage。所以 `createModelRegistryFromProfiles` 一次性把所有可用 profile 的 apiKey 按 provider 预注册，并预建 Model Map 供切换查表。

## 九、面试高频追问预案

### Q1：为什么 Agent 工具不直接在后端执行？
A：见 1.1。核心是画布状态在浏览器、Python 必须在浏览器（Pyodide）。前端执行型架构让工具执行端可插拔，且避免双状态同步地狱。

### Q2：事件流为什么用 SSE？为什么不是原生 EventSource？

**最终选型**：标准 SSE（`text/event-stream`，帧格式 `data: {json}\n\n`），但用 `fetch` + 手写解析，**不用原生 `EventSource` API**。

**关键厘清**：SSE 有两种实现。原生 `EventSource` 不支持自定义 header（[whatwg/html#2177](https://github.com/whatwg/html/issues/2177)），而项目硬约束要求所有请求走统一 axios 注入 JWT——原生 EventSource 直接排除。剩下只能"fetch 手写 SSE 解析"，前端解析逻辑在 `src/services/parseSseStream.ts`（按 `\n\n` 分帧 + 剥 `data:` 前缀 + 跨 chunk buffer）。

**演进过程（诚实复盘）**：最初选了 NDJSON（一行一个 JSON），理由是格式更裸、前后端对称。后来主动演进到 SSE，真实理由：① 对齐业界主流（OpenAI/Anthropic/Gemini 全用 SSE），降低新人认知和抓包调试成本；② 改造成本极低（后端写帧加 `data: ` 前缀 + 改 Content-Type，前端解析换分隔符）。

**关于自动重连的刻意取舍**：SSE 原生有 `retry:/id:` 自动重连，但 Agent 会话有状态，偷偷续传反而是负担——我们要的是"断了 GET 快照手工重建"（`recoverSessionState`）。所以手写解析时刻意不依赖这些字段，只用 `data:`，重连由快照恢复兜底。事件类型放在 JSON 的 `type` 字段里，不重复使用 SSE 的 `event:` 字段。

⚠️ 简历/面试里讲这个点，亮点是**"对齐业界 + 刻意取舍自动重连"的工程判断**，而不是协议本身——协议只是载体。

### Q3：Agent 在思考时用户发消息怎么办？
A：见 1.2。responding 态用 followUp 插话，tooling 态排 pendingFollowUps 队列，以 toolResult 结束的能用 continue 续跑。

### Q4：浏览器跑 Python 怎么保证安全？
A：见 3.3。六层纵深防御，重点讲 L3 jsglobals 锁定 + L4 Worker 能力剥夺 + L5 超时配额 + 20 项红队回归。

### Q5：Pyodide 文件系统怎么和持久层对接？（含"为什么不用官方 mountNativeFS / 自研会不会更不稳"）

**核心定位（一定要这么说）**：我们没有"自研文件系统"，是**绕开了 Pyodide 一个不稳的集成点，用两个稳的组件 + 薄胶水替代**。用 MEMFS（Pyodide 自带）+ OPFS（浏览器原生）双层，中间自己写 sync，不挂官方 `mountNativeFS`。

**三个理由（都能对上官方文档，硬证据）**：

1. **官方 `mountNativeFS` 默认就不同步**——Pyodide 官方 file-system 文档原话：*"Due to browser limitations, the changes in the mounted file system is **not synchronized by default**. In order to persist any operations to an native file system, you must call `await nativefs.syncfs()` or `pyodide.FS.syncfs(false, callback_func)`"*。这是浏览器沙盒的硬限制，**用官方方案我们也得手动 sync**，所以"手动 sync"这个代价躲不掉，那不如把 sync 逻辑写在自己手里。

2. **官方 `mountNativeFS` 是 Experimental，仅支持 Chromium**——它依赖 File System Access API，Firefox/Safari 不支持。官方整段标题就是 *"(Experimental) Using the native file system in the browser"*，明确写了 *"only supported in Chromium based browsers: Chrome and Edge"*。

3. **项目风险登记的实证**——`docs/design-doc/notebook-agent/验收与基线.md:265` 风险登记表：「Pyodide OPFS 直挂在 0.27.x 不够稳定 — 等级：中 — 缓解：PoC 阶段验证；不行降级到 IDBFS-like + iframe 主动 sync」。具体不稳的是 emscripten NODEFS 接 OPFS 的集成点（NODEFS → File System Access API → OPFS 三层）。

**对照表**：
| 维度 | 官方 `mountNativeFS` | 我们的"双 FS" |
|------|---------------------|--------------|
| 同步 | 必须手动 `syncfs()` | 必须手动 sync（**一样**）|
| 浏览器兼容 | 仅 Chrome/Edge（Experimental）| 跟随 OPFS，不被 Experimental 标签拖累 |
| 依赖链 | emscripten NODEFS → File System Access API → OPFS（三层集成点，0.27 未充分验证）| MEMFS（自带，稳）+ OPFS（原生，稳）+ 自己写的薄 sync |

**当前具体实现（逐环节，全部带代码锚点）**：

- **Boot 只 mkdir，绝不 mount**（`pyodideBoot.ts:187`）：只在 MEMFS 建四个顶级目录 `/inputs /scripts /artifacts /reports`，注释明写"OPFS 才是事实持久层，MEMFS 用作 Pyodide 可见工作区，双向 sync"。
- **OPFS 走浏览器原生 handle 链**（`opfsAccess.ts`）：`writeFile/readFile` 全基于 `navigator.storage.getDirectory()` 的 `FileSystemDirectoryHandle`，完全不碰 Pyodide FS；带 `resolveSafePath` 路径强校验 + 500MB/50MB 配额。
- **入向 sync（OPFS→MEMFS）`syncOpfsFilesToWorker`**（`notebookSessionRuntime.ts:297`）：`readBytes(OPFS)` → `workerHost.writeFs`（postMessage → Worker 内 `pyodide.FS.writeFile`）。触发点：启动期、Worker 重启后（`onAutoRestarted:400`）。
- **出向 sync（MEMFS→OPFS）`syncWorkerFilesToOpfs`**（`:287`）：`workerHost.snapshotFs(paths)`（postMessage 让 Worker 把 MEMFS 文件拉出来）→ `writeFile(OPFS)`。触发点：
  - 每次 `python_exec_*` 完成后，同步 artifacts/reports/scripts（`handleToolExecute:452`，**这就是 savefig 闭环 B6**）
  - 定时轮询 artifacts/reports（`pollTimer:572`，`FILE_TREE_POLL_MS` 间隔）
  - 主站 `import_csv` 后通知（`onWorkspaceChanged:544`）
  - Agent 单文件 `fs_write/fs_edit` 后（`syncSinglePathToWorker:325`，严格语义）
- **跨设备恢复**：exec 落盘后 best-effort 上传 workspace zip 到服务端（`pushWorkspaceSnapshot:467`），OPFS 空时从服务端拉回（`restoreWorkspaceIfEmpty:357`）。

**诚实交底的三个代价（面试官必追问，主动说）**：
1. **出向 sync 有窗口**：exec 后才主动 snapshot，轮询兜底。Worker 在下次 sync 前崩了，文件可能丢在 MEMFS。**应对**：Worker 重启从服务端 zip 快照恢复（退到上次 exec 后状态）。
2. **大文件双写内存翻倍**：入向 OPFS+MEMFS 各一份。**应对**：50MB 单次上限 + 500MB session 配额。
3. **比官方 `mountNativeFS` 多写 sync 代码**：但官方也要 `syncfs()`，我们只是把 sync 写在自己手里，可控可测。

**一句话总结**（面试可直接背）：「我们没用官方 `mountNativeFS`，因为官方文档自己说默认不同步、还得手动 `syncfs()`，而且它是 Experimental 只支持 Chromium；项目风险登记也写着 0.27 直挂不稳。所以我们用 MEMFS（Pyodide 自带）+ OPFS（浏览器原生）+ 自己写的薄 sync——两个稳的组件加一段我能 debug 的胶水，比赌上游黑盒可靠。代价是出向 sync 有窗口，所以每次 exec 后还 best-effort 上传 zip 到服务端做兜底。」

### Q6：Agent 工具调用怎么和前端配对？
A：toolCallId 全流程配对。后端 bridge.request 返回挂起 Promise + 启超时；前端 tool.execute 事件带同一 toolCallId；前端 POST tool-result 回传；bridge.resolveResult(toolCallId) resolve Promise。前端每 10s 发 tool-progress 续期。

### Q7：bootstrap 竞态是怎么发现的？
A：见 3.6。events 订阅即触发 prompt，结果 Agent 第一轮 fs_list 时 CSV 还没写完。改成 events 订阅 + data ready 双条件 + 一次性触发，配 E2E 回归。

### Q8：为什么有废弃的 workflow-ai 和 opencode？
A：见 8.1。workflow-ai 一次生成 JSON 易错且不能自验证；opencode 耦合重。迁到 Pi Agent 工具调用模式后能渐进式构建 + 自我验证。删了但留 404 回归。

### Q9：双存储抽象怎么实现的？
A：见 6.2。统一 Repository 接口，工厂按环境变量切换 LowDB/MySQL，组合根注入，历史大对象上 S3。

### Q10：工作流执行引擎怎么处理依赖？
A：见 5.1。拓扑递归——单节点执行先递归跑上游，全局执行选 Terminal 节点逐个跑。支持冻结复用、调试策略、运行时补参、停止标记。
