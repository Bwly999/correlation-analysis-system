# 工作流模板体系 MVP 设计

## 背景

当前工作流系统已经具备节点编排、运行、帮助中心与结果展示能力，但新用户第一次进入工作流模块时，仍然需要自己决定：

- 应该从空白画布开始，还是直接套用常见分析链路
- 哪些节点适合组成一条最小可运行的分析流程
- 怎样更快创建“能跑通”的工作流骨架

`P2-1` 的目标不是一次做完整模板中心，而是先提供最小可用的分析模板体系，帮助用户快速上手和创建工作流。

## 本轮目标

- 定义统一的工作流模板数据结构
- 提供 4 个内置分析模板
- 在工作流头部和工作流管理中心提供模板入口
- 支持从模板一键创建新的未保存工作流
- 为每个模板补齐最小中文说明

## 非目标

- 不做模板预览页
- 不做模板参数向导
- 不做模板导入导出复用
- 不做帮助中心深度联动
- 不做模板收藏、搜索、分组筛选

## 已确认设计结论

1. 本轮采用“模板注册表 + 统一入口 + 一键落图”的最小实现。
2. 模板链路优先保证“结构清晰、节点数量少、可继续编辑”。
3. 模板创建后直接进入新的未保存工作流，不增加二次确认步骤。
4. 每个模板只提供最小中文说明，不做详细使用教程。

## 总体方案

### 1. 模板数据层

新增独立模板注册模块，统一维护模板元数据与节点骨架，避免把模板结构散落在组件中。

建议最小数据结构：

```ts
interface WorkflowTemplateDefinition {
  id: string
  name: string
  description: string
  recommendedNextStep: string
  build: () => {
    workflowName: string
    nodes: Array<{
      type: string
      label?: string
      position: { x: number; y: number }
      config?: Record<string, unknown>
    }>
    edges: Array<{
      sourceIndex: number
      targetIndex: number
    }>
  }
}
```

约束：

- 模板模块只声明骨架，不直接操作 store
- store 负责把模板骨架转换成真实工作流节点与边
- 模板中的节点配置优先复用节点定义已有默认值，只补最少必要字段

### 2. Store 职责

`workflowStore` 新增“从模板创建工作流”的能力，负责：

1. 清空当前编辑态工作流
2. 根据模板骨架创建节点
3. 连接模板定义中的边
4. 设置新的工作流名称
5. 重置当前工作流 id 为 `null`
6. 标记当前工作流为未保存状态
7. 触发画布视图复位

这样模板创建逻辑只存在一处，`WorkflowHeader` 和 `WorkflowManagerModal` 都复用同一条 store 链路。

### 3. UI 入口

本轮提供两个入口：

- `WorkflowHeader`
  - 在“新建”旁提供模板创建入口
  - 作为首次进入工作流时的高可见快捷入口

- `WorkflowManagerModal`
  - 在管理中心顶部创建区补充“从模板创建”
  - 方便已有用户在管理工作流时直接复用模板

交互原则：

- 点击模板后直接创建新工作流
- 创建完成后关闭管理弹窗并回到画布
- 不做预览、不做确认、不做额外表单

## 模板范围

本轮内置 4 个模板，全部采用“最小可跑通链路”：

### 1. 相关性排查模板

骨架：

- `file-import`
- `field-selection`
- `pearson`

目标：

- 帮助用户快速搭出最常见的相关性分析起手式

### 2. 关键因子筛选模板

骨架：

- `file-import`
- `field-selection`
- `random-forest-feature-importance`

目标：

- 帮助用户快速进入特征重要性筛选流程

### 3. 变量解释分析模板

骨架：

- `file-import`
- `field-selection`
- `xgboost-shap`

目标：

- 帮助用户快速进入变量解释分析流程

### 4. 看板数据对比分析模板

骨架优先采用更稳妥的最小链路：

- `file-import`
- `data-aggregation`
- `chart-display`

目标：

- 帮助用户先完成一条易理解的数据对比链路，避免首期模板因多输入配置过重而降低可用性

## 组件边界

### `WorkflowHeader`

- 负责展示模板入口
- 通过事件把模板选择结果上抛给父组件
- 不直接访问模板创建细节

### `WorkflowManagerModal`

- 负责展示模板卡片列表
- 通过事件把模板 id 上抛给父组件
- 不直接拼接节点与连线

### `WorkflowCanvas`

- 负责承接头部与管理中心事件
- 调用 `workflowStore` 的模板创建方法
- 复用现有未保存改动保护逻辑

## 测试策略

本轮按 TDD 先补失败测试，再实现功能。

至少覆盖：

- store 可根据模板创建新的工作流骨架
- 创建后工作流名称、节点数、边数符合模板定义
- 创建后 `currentWorkflowId` 为 `null`
- 创建后当前工作流为未保存状态
- 头部和管理中心能够触发模板创建事件

## 文档同步

本轮会新增工作流模板入口与模板创建链路，需要更新：

- `工作流系统.md`
  - 补充模板入口与一键创建工作流说明

本轮不改节点协议与节点创建规范，因此不要求更新 `工作流节点说明.md`。

## 风险与缓解

### 风险 1：模板骨架过重，新手反而更难理解

缓解：

- 每个模板严格控制在 2 到 4 个节点
- 优先做最小可运行链路，不提前塞入复杂增强步骤

### 风险 2：模板逻辑散落在多个组件中，后续难维护

缓解：

- 模板定义集中在独立注册模块
- 创建逻辑集中在 store
- 组件只负责展示与事件转发

### 风险 3：模板节点默认配置不稳定

缓解：

- 优先依赖节点定义默认值
- 模板层只补最少必要配置

## 最终结论

`P2-1` 本轮采用“模板注册表 + store 创建逻辑 + 双入口触发 + 一键落图”的 MVP 路线。

该方案可以在较小改动下提供：

- 更快的首次上手路径
- 更低的工作流创建门槛
- 后续扩展模板中心、导入导出和帮助联动的稳定基础
