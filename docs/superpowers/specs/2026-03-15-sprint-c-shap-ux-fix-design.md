# Sprint C SHAP 体验修复设计

## 目标

完成 `ROADMAP.md` 中 Sprint C 的 4 项工作，并以“前端体验优先”为核心原则重组 SHAP 分析结果：

- 修复前后端图表不一致
- 修复整合大图展示
- 完善导出
- 补全端到端验证

本次不追求机械复刻后端 Python 图表，而是要让用户在前端看到一套清晰、稳定、可导出的主报告。同时保留后端整图作为补充视图与归档能力。

## 当前问题

### 1. 结果结构以“双视图并列”组织，叙事冲突

当前 `src/nodes/definitions/xgboostShap.ts` 直接生成两个并列 tab：

- 前端分图视图
- 后端整图视图

这会导致用户在同一次分析中看到两套并行叙事：

- 前端图表强调可读性和局部分析
- 后端整图强调算法原始输出和全量排版

二者同时作为一级入口，会造成信息重复、结构冲突和阅读路径不清晰。

### 2. SHAP 前端展示未形成统一信息架构

当前前端结果由文本、柱状图、蜂群图、依赖图、整图临时拼接而成，缺少稳定的“主报告顺序”。这会带来几个问题：

- 首屏噪音大，用户难以把握重点
- 关键因子与全部因子之间没有明确层级
- 趋势图和整图的职责边界不清楚

### 3. 全量因子可达性不明确

当前逻辑会优先展示前若干重要因子，但“默认展示部分”和“实际支持全部浏览”之间没有清晰约束。Sprint C 需要明确：

- 默认可以只展示部分因子
- 但全部因子必须可检索、可切换、可查看、可导出

### 4. 导出语义混乱

当前导出逻辑同时处理前端报告截图与后端大图下载，但没有清晰区分：

- 用户导出的到底是当前前端报告状态
- 还是后端原始整图

这会导致“页面看到的是 A，导出得到的是 B”的体验落差。

### 5. 验证链路不足

现有测试覆盖了 SHAP 节点基本执行，但尚未系统覆盖：

- 新报告结构
- 全量因子浏览能力
- 导出分支
- 页面与补充整图的协同关系

## 方案选择

采用“前端主报告 + 后端补充视图”的方案。

### 方案原则

- 前端报告承担主阅读路径
- 后端整图退为补充视图，不再与主报告平级竞争
- 返回结果以结构化数据优先，图片资源作为补充资产
- 默认展示部分因子，但必须支持全部因子的浏览、搜索、切换与导出

### 不采用的方案

不采用“仅修补现有 tabs 文案和图表标题”的保守方案，因为这无法真正解决双视图冲突。

不采用“完全以后端整图为主，前端只做包装”的方案，因为这不符合本次“以前端体验优先”的目标。

不采用“彻底重写后端绘图体系”的重构方案，因为 Sprint C 的定位是体验修复与收口，不是全栈重构。

## 设计

### 1. 主报告信息架构

SHAP 分析结果统一收敛为单一主报告，默认阅读顺序固定为 4 个部分：

1. 模型摘要
2. 特征贡献排行
3. 关键因子趋势
4. 完整因子明细

#### 模型摘要

展示对整份报告的最小必要上下文：

- 目标字段
- 样本量
- 特征数
- `R²`
- `MAE`

其作用是先回答“本次模型分析了什么、质量如何”，而不是让用户先掉进图表细节。

#### 特征贡献排行

作为全局导航入口，展示按重要性降序排列的特征贡献柱状图。

要求：

- 默认显示前 `N` 个高重要性因子
- 保持重要性排序稳定
- 提供定位任意因子的能力
- 可作为后续趋势区与明细区的跳转入口

#### 关键因子趋势

这里不再硬编码“只看前几个然后结束”，而是：

- 默认先展示前 `K` 个高重要性因子
- 支持切换到任意因子
- 支持按重要性顺序前进/后退
- 支持缩放或局部浏览

关键约束：

- 默认只露出部分因子是为了降噪
- 但所有因子都必须可以进入这一视图

#### 完整因子明细

承载全部因子的逐项查看能力。

要求：

- 按重要性排序列出全部因子
- 默认只渲染一部分，避免一次性铺满
- 支持搜索、分页、显示更多或等价机制
- 每个因子都可以展开查看自己的趋势图和基础统计

### 2. 后端整图的角色调整

后端 `full_report_image` 保留，但不再作为和主报告平级的第二个分析主页面。

它的角色调整为“补充视图”：

- 名称改为“后端原始整图”或等价中文名称
- 作为次级入口提供
- 主要用于对照、归档和单独导出

这样可以确保：

- 用户默认只看到一套前端主叙事
- 后端整图仍可访问
- 不再出现两套一级视图争夺注意力

### 3. 数据契约收敛

后端继续负责模型训练与 SHAP 计算，但返回结构从“图片优先”调整为“结构化数据优先”。

建议返回模型：

```ts
type ShapSummary = {
  targetField: string
  sampleCount: number
  featureCount: number
  r2: number
  mae: number
}

type ShapImportanceItem = {
  name: string
  value: number
  rank: number
}

type ShapDependenceItem = {
  feature: string
  x: number[]
  shap: number[]
  actualY?: number[]
  xRange?: [number, number]
  shapRange?: [number, number]
}

type ShapAssets = {
  beeswarmImage?: string
  fullReportImage?: string
  dependenceImages?: Array<{
    feature: string
    image: string
  }>
}
```

返回结果至少应包含：

- `summary`
- `importance`
- `dependence`
- `assets`

其中：

- `importance` 必须是全量因子，按降序排列
- `dependence` 必须覆盖全量因子
- `assets.fullReportImage` 保留
- `assets.dependenceImages` 仅作为兼容或兜底资源，不再作为主路径依赖

### 4. 前端报告模型

`src/nodes/definitions/xgboostShap.ts` 不再临时拼接双 tab 结构，而是先将后端响应归一为统一 report model，再交给 `ReportViewer` 渲染。

建议方向：

- 去掉当前“前端分图 / 后端整图”的平级 tabs 设计
- 改为单一 `report.sections`
- 将补充视图入口放到 `report.supplements`、`report.assets` 或等价区域

这样可以让：

- 页面渲染逻辑统一
- 导出逻辑基于同一份模型
- 后续测试只验证一套主报告结构

### 5. 交互设计

Sprint C 至少提供以下 3 类交互控制。

#### 因子范围控制

- 默认显示前 `K` 个高重要性因子
- 支持显示更多与收起
- 支持按因子名搜索

#### 趋势浏览控制

- 提供因子选择器
- 支持按重要性顺序切换上一项/下一项
- 支持缩放、局部查看或等价交互

#### 补充视图入口

- 为后端原始整图提供单独入口
- 可预览
- 可单独导出

### 6. 导出设计

导出必须显式区分两种语义。

#### 导出当前主报告

导出用户当前前端报告状态，内容应与页面保持一致：

- 当前筛选
- 当前展开区块
- 当前图表

这是一份“前端阅读版导出”。

#### 导出后端原始整图

直接导出后端 `fullReportImage`，并在文案上明确这是“后端原始整图”。

这样可以避免用户误解两个导出入口的语义。

### 7. 错误处理

需要保持并强化以下行为：

- 后端错误真实透传，不回退为假数据
- 当结构化数据不完整时，前端明确降级展示
- 当补充整图缺失时，不影响主报告可读性
- 当某个因子的依赖数据缺失时，局部显示异常提示，不拖垮整份报告

## 测试策略

Sprint C 至少补齐 3 层验证。

### 1. 节点单测

验证：

- SHAP 节点生成新的 report 结构
- `importance` 为全量因子
- `dependence` 为全量因子
- 补充整图入口存在

### 2. 报告组件单测

验证：

- 默认仅展示部分因子
- 搜索可定位任意因子
- 显示更多或分页机制可访问全部因子
- 补充视图入口存在
- 导出分支根据当前模式走对逻辑

### 3. 端到端验证

至少跑通一次真实 SHAP 数据链路，确认：

- 页面主报告可正常打开
- 全量因子可访问
- 后端原始整图可预览或导出
- 页面导出与原始整图导出语义清晰

## 分阶段交付

1. 收敛后端接口返回结构
2. 重构 `xgboostShap` 节点的报告模型拼装
3. 重组 `ReportViewer` 的 SHAP 主报告展示
4. 补充后端原始整图的补充视图入口
5. 修正两类导出逻辑
6. 补齐单测与端到端验证

## 非目标

本次不做：

- 全面重写 Python SHAP 绘图体系
- 将所有后端图片全部替换为前端重绘
- 引入新的通用报表 DSL
- 扩展到非 SHAP 算法节点的统一重构
